Conjugate Compilation：把草稿与大模型放进同一个编译边界

arXiv:2610.25012 · 2026年10月18日提交 · UCSD / MIT / UT Austin / 微软 · 实验：NVIDIA B300 与 RTX 5090

一句话：它不提出新的投机解码算法，而是把编译器的优化边界从"单个模型"扩到"同一张卡上的 draft + target 两个模型"——用共置执行后的实测性能来指导跨模型编译决策，把两个模型各自跑不满 GPU 时浪费的碎片算力捡回来。

01问题：两个模型在合作，编译器却各管各的

投机解码里，小 draft 模型先出 γ 个草稿 token，大 target 模型一次前向验证。传统部署中两个模型分别编译、顺序执行：γ 步草稿全部跑完，验证才开始。设单步草稿耗时 TD、验证耗时 TV，则：

Tconventional=γ TD+TVT_{\text{conventional}} = \gamma\,T_D + T_V

绿色段与紫色段完全串行，同一时刻总有一块算力在等（论文图2a）

作者引用的测量显示企业用户 GPU 平均利用率仅 17.6%，94% 的用户低于 50%。此前的并行投机解码系统（PEARL、SwiftSpec、FASER）解决的是调度与放置，编译仍然各自独立——两个模型的共享执行落在编译器的优化边界之外，这就是本文要收复的地盘。

传统：串行
共调度：跨 batch 重叠
再加交织 kernel
draft 草稿段 target 验证段 两模型交织进同一 kernel

示意（对应论文图2，数据为 Llama-3.2-1B 草稿 + Llama-3.1-8B 目标，γ=4）：单轮 31.3ms → 22.0ms → 19.7ms，最好情况 1.59 倍。

02三层设计：共调度 → 联合编译 → 交织算子

第一层 · 依赖保持的双流共调度

依赖只在同一个 batch 内成立：target 验证第 b 批的草稿前必须等它出完；但 target 验证 b 时，draft 完全可以给第 b+1 批出草稿。于是把两个模型切成更细的段（到层、attention/MLP 半段、单个投影级），放上两条 CUDA stream，只在必要的依赖处插同步事件，整轮捕获成一张 CUDA 图重放，消除发射开销。

第二层 · 以共置执行的实测为准（全文最关键的一条洞见）

单独测得快的 kernel，两个模型一起跑时未必快——它可能加剧资源争用、破坏原本有益的重叠。所以联合优化方案的价值不能分解成单个 kernel 的收益之和：

Tround(θ)  ≠  Tround(∅)−∑g∈G(θ)(∑ok∈gτ(ok)  −  τ(g))T_{\text{round}}(\theta) \;\neq\; T_{\text{round}}(\varnothing) - \sum_{g \in \mathcal{G}(\theta)} \Big( \sum_{o_k \in g} \tau(o_k) \; - \; \tau(g) \Big)

τ(o) 是算子单独执行的时延，τ(g) 是拼成一个跨模型组后的时延

于是优化目标从"每个 kernel 更快"改成"整轮共享执行更快"：

θ∗=arg⁡min⁡θ∈ΘlegalTround(θ)\theta^{*} = \arg\min_{\theta \in \Theta_{\text{legal}}} T_{\text{round}}(\theta)

每个候选方案都要完整编译、跑通数值校验后按整轮时延打分

第三层 · 跨模型交织 kernel（interleaved kernels）

把两个模型的算子按算术量占比拼进同一次发射：每个 GEMM 成员拆成输出 tile × reduction slice 单元，交织比例直接由各成员的算术量占比决定：

πk=Fk∑r=1KgFr\pi_k = \dfrac{F_k}{\sum_{r=1}^{K_g} F_r}

Fk 是成员算子的算术工作量

描述符表记录每个单元属于哪个成员、坐标和数据地址，各单元只读写自己的数据，数学结果不变。RMSNorm、残差加这类行操作同样支持。Roofline 显示 Llama 下投影两个 kernel 串行合计 17.9 TFLOP/s，交织后 46.5 TFLOP/s（2.6 倍），更贴近带宽屋顶。

03谁来搜方案：LLM agent + 蒙特卡洛树搜索

联合方案的组合空间太大且每个候选都要编译加实测才能知道好坏，论文把它交给一个自提升循环：agent（GPT-5.6）不直接写 kernel，而是在方案抽象层做 add / merge / split / remove 四种编辑；MCTS 决定下一步细化哪个节点；编译器做静态合法性检查并对每个新交织组设增益门控：

v(g)=∑kτ(ok)τ(g)  >  1+max⁡(δ,  z⋅s)v(g) = \dfrac{\sum_{k} \tau(o_k)}{\tau(g)} \; > \; 1 + \max(\delta,\; z \cdot s)

门控要求交织组的整体收益显著超过单独 kernel 之和，并考虑测量噪声

方案被选中后由 MCTS 按置信上界展开：

θt=arg⁡max⁡θ′∈ch(θ)[Q(θ′)+βln⁡(N(θ)+1)N(θ′)]\theta_t = \arg\max_{\theta' \in \mathrm{ch}(\theta)} \left[ Q(\theta') + \beta \sqrt{\dfrac{\ln\big(N(\theta)+1\big)}{N(\theta')}} \right]

N 为访问次数，Q 为归一化的平均回传奖励

MCTS 选节点决定细化哪个已探索方案
→
LLM 提出编辑基于历史方案、实测分数、kernel 判定和编译器反馈
→
编译器构建合法性检查、调优交织 kernel
→
GPU 实测整轮数值校验通过才计分，奖励回传更新搜索树

失败信息（编译拒绝码、未过门控的 kernel 判定）同样回喂给 agent。整轮搜索是离线编译期工作，推理时不增加任何运行时开销。

  • 仅联合编译：6 组配置几何平均 1.37×；加交织 kernel 后 1.45×，最好情况 1.59×。
  • GPU 利用率平均提升 1.46×（5090）/ 1.50×（B300）；Llama 组从 11.6% 提到 18.7%——绝对值仍不高，说明它吃的是碎片余量，不是让卡跑满。
  • 敏感性：batch 8→16 时加速从 1.34× 降到 1.22×；草稿长度 γ=4→6 时从 1.55× 降到 1.37×。每个模型自身工作越满，可捡的跨模型余量越小。

05边界与判断

已确认论文实测范围内成立

单 GPU、batch ≤ 16、输入 1024 token、FP16、静态负载。数值校验要求相对误差 10⁻² 以内，输出保持无损。

推断适用场景

低并发、单卡推理（本地部署、端侧）最受益；在线大 batch 服务场景收益递减，1.37× 未必保得住。搜索成本是每次模型组合更换时的一次性离线投入。

推断方法论价值大于具体数字

"编译决策以共置执行的实测为准"这条路不限于投机解码，对多模型共卡 serving、agent 驱动编译（KernelBench、STARK 一类）都有借鉴：搜索空间从"单个 kernel 代码"扩到了"跨模型方案组合"。

术语：draft / target —— 草稿 / 目标模型；γ —— 每轮草稿长度；交织 kernel —— 把多个算子的数据块拼进一次 kernel 发射；MCTS —— 蒙特卡洛树搜索；Roofline —— 以算力/带宽上限为参考的性能分析。
