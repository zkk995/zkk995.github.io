投机解码无损加速草稿树异步预取训练无关

DICE：验证用的随机数先抽好，投机解码白捡 24.6% 吞吐

Speculative Decoding Is Less Speculative Than You Think
Guanning Zeng, Andrea Zanette · Carnegie Mellon University · arXiv:2611.27891 v1 2026-11-20

一句话：投机解码的成败取决于「把有限的起草算力花在目标模型真正会走的路径上」，而这背后有两份不确定性——目标模型的预测（要花一次前向才知道）和采样随机数（起草之前就能定下来）。DICE 把后者变成免费信息：预先抽好验证要用的随机数，让起草和验证共用同一份「骰子」，草稿树和预取缓存都朝「这次采样真正会接受的方向」倾斜。不改草稿模型、不改输出分布，在 18 组模型-后端配置上全部拿到加速，最高比强基线快 24.6%。

1. 问题：起草算力该花在哪，其实有一半答案早就知道了

投机解码的效率核心是个算力分配问题：草稿模型不可能穷举所有续写路径，树往哪边长、缓存预取哪些草稿，决定了验证时能白拿多少 token。以往的工作几乎全在攻第一份不确定性——把草稿分布 qq 往目标分布 pp 上靠（EAGLE 系列、各种训练方法）。本文盯住的是第二份：采样随机性。

标准投机采样里，提案 xx 被接受的条件是：

u q(x)≤p(x)u\,q(x) \le p(x)

关键观察：给定 q(x)=0.5q(x)=0.5，如果这次抽到的 u=0.1u=0.1，那只要 p(x)≥0.05p(x)\ge 0.05 就会接受——值得顺着 xx 往深里看；如果 u=0.9u=0.9，则要 p(x)≥0.45p(x)\ge 0.45 才行——不如多备几条退路。目标概率还不知道，但接受阈值已经知道了。同一份草稿预测，配上不同的已知随机数，最优的算力分配完全不同。目标采样用 Gumbel-max 技巧实现时，扰动 gg 同样可以在起草前生成。

2. 方法：把「骰子」同步给起草方和验证方

DICE（Draw-Informed Candidate Selection）的做法：验证要用的随机数（接受判定的均匀数 uiu_i、目标采样的 Gumbel 向量 gig_i）先抽好，起草策略和目标验证器共用同一份。草稿模型照常用，输出分布分毫不改——同样的随机数下，生成序列与自回归目标采样逐 token 一致（附录有正确性证明）。两个落点：

2.1 种子感知草稿树

在每个节点 xx，用草稿 logits dxd_x 加上已知的 Gumbel 扰动，估计目标的下一个 token 选择：

r^x(v)=softmaxv ⁣(α dx+T g∣x∣+1σ)\hat r_x(v) = \mathrm{softmax}_v\!\left(\frac{\alpha\, d_x + T\, g_{|x|+1}}{\sigma}\right)

整条路径的得分沿路累乘，w^(x)\hat w(x) 估计「这个节点会被验证访问到」的可能性：

w^(∅)=1,w^(xv)=w^(x) r^x(v)\hat w(\varnothing)=1,\qquad \hat w(xv) = \hat w(x)\,\hat r_x(v)

这套得分贯穿树构建全程：每步选哪些子 token、扩展哪个节点、最终挑哪 NN 个节点送去验证，全由它说了算。超参 (α,σ)(\alpha,\sigma) 每对目标-草稿模型只校准一次，头 2000 个节点（约 1–3 条 prompt）就够。EAGLE-2/3/4、独立小草稿器、MTP 模块全部即插即用。

2.2 种子感知异步预取

SSD 这类方法在验证当前提案时，预先给下一轮可能的验证结果 (k,v)(k,v)（接受长度 + 修正 token）备好草稿，缓存只能放 BB 条。DICE 用已知随机数估计每个结果的可能性：接受长度由 uiu_i 预测——对未知概率比 ρi=pi(xi)/qi(xi)\rho_i=p_i(x_i)/q_i(x_i) 做最大熵建模（假设草稿校准 E[ρi|qi(xi)]=1\mathbb{E}[\rho_i|q_i(x_i)]=1，得截断指数分布），再算接受概率：

η^i=Pr⁡ρ∼fqi(xi) ⁣(ρ≥ui)\hat\eta_i = \Pr_{\rho\sim f_{q_i(x_i)}}\!\left(\rho \ge u_i\right)

修正 token 用同一套比例模型加已知 Gumbel 向量预测，两者相乘得到每个验证结果的估计概率，取 top-BB 去预取。草稿本身不变，只是「备哪几份」变聪明了。

2.3 工程实现

随机数用「请求种子 + 绝对 token 位置（+ 词表下标）」索引的确定性计数器哈希按需生成，接受、目标采样、草稿提案各走独立随机流。起草和验证即使在不同 GPU 上也能各自算出同一份随机数，不用存也不用传；打分融合进现有 GPU 候选选择核，能被 CUDA graph 捕获，零额外前向。

3. 实验：18 组配置全赢，温度越高赚越多

3.1 草稿树解码

16 组目标-草稿对（独立草稿器 + EAGLE-2/3/4 + MTP），HuggingFace / SGLang / vLLM 三种后端，H200、T=1、并发 1。DICE 在每一个配置上都超过原基线：Spec-Bench 提升 4.3–21.5%，SPEED-Bench 提升 5.6–24.6%。挑几行看：

两个很实用的趋势：温度越高赚得越多——T=0 时大家都是贪心验证、速度相同；温度升高后固定预算的树越来越盖不住采样路径，EAGLE-4 吞吐下滑，DICE 因为树是照着「真会用的随机数」搭的，下滑慢得多。并发越高优势越稳——并发 1 到 64 全程最快，SGLang/vLLM 里领先最强基线 2–18% / 8–20%；并发 64 时 DFlash2 和 DSpark 已经掉到比自回归还慢，DICE 仍保持 1.19× / 1.28×。

3.3 增益到底从哪来：消融做得干净

  • 不是加噪声的功劳：把随机数换成与验证无关的打乱版本，接受长度反而掉 11–14%；同步真随机数则涨 11–24%。增益来自「知道目标真会用哪份骰子」，不是扰动本身。
  • 增益必须作用在预算分配上：只用随机数选子节点、预算仍按草稿概率花，大部分收益消失。DICE 让树在第一个 token 之后的每个深度都更盖得住目标的真实路径，深度越深差距越大。
  • 预算等价换算：EAGLE-4 要 64 个节点才能达到 DICE 16 个节点的接受长度；SSD 要 24 条缓存才追平 DICE 8 条的命中率。
  • 两类随机数各有贡献：接受数 uiu_i 指出验证会在哪停，Gumbel 向量指出后面跟哪个 token；单用任一类把命中率从 59.8% 提到 66.9–67.9%，合用 76.2%。
  • 不需要精确建模目标：最朴素的 plug-in 规则（α=σ=1）就有 9–22% 增益，校准再加 1–2 个点，换神经预测器最多再加 1.5 个点。增益靠的是「用真随机数排序候选」，不是「精确算出目标分布」。

4. 我的看法

  • 这是那种「说出来人人都懊悔没先想到」的观察：采样随机数本来就是要生成的，把它从「验证之后才揭晓」挪到「起草之前就同步」，等于把一份已经付费的信息变成了决策依据。整个方法没有新模型、没有训练、没有分布改动，却是在生产引擎（SGLang/vLLM）里实打实的两位数吞吐增益——性价比极高的一类工作。
  • 与近期几条线正交：ALD（arXiv:2611.27477）压的是草稿模型内部的串行，PEARL/DPara 压的是起草与验证之间的串行，DICE 压的是「算力往哪分配」——三者叠在同一个草稿器上理论上互不冲突。和 Saguaro 的组合实验也证明了互补性。
  • 两个落地前提要留意：一是预取侧假设草稿校准（E[ρ|q]=1\mathbb{E}[\rho|q]=1），草稿器没校准好时估计会偏，好在消融显示对估计形式不敏感；二是确定性哈希随机数要求引擎端到端接管采样种子——用户自带种子、或引擎 RNG 策略不同的场景，接入时要动采样管线，这不是纯插件能覆盖的。
  • 天花板仍在草稿器：DICE 优化的是「给定草稿质量下的分配效率」，草稿分布本身离目标太远时，再聪明的分配也省不出 token。它是现有草稿器生态（EAGLE/MTP）的放大器，不是替代品。
